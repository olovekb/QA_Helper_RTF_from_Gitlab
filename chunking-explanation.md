# Объяснение чанкизации в проекте

## Что здесь вообще называется чанкизацией

В этом проекте есть не одна, а две разные чанкизации:

1. Семантическая чанкизация требований для RAG и поиска контекста.
2. Разбиение уже готовой тестовой модели на батчи для генерации тест-кейсов.

Из-за этого слово `chunk` встречается в коде в нескольких местах, но смысл у них разный.

## 1. Семантическая чанкизация требований

Основная реализация находится в `server/semanticChunking.mjs`.

Точка входа: функция `chunkify(markdown, metadata)`.

### Общий принцип

Код режет документ не по фиксированному числу токенов и не по числу символов, а по смысловым секциям документа:

- бизнес-правила;
- UI-правила;
- API-контракты;
- правила валидации;
- обработка ошибок;
- шаги сценариев;
- справочный контекст;
- строки таблиц;
- шумовые/служебные блоки.

Идея такая: один chunk должен по возможности содержать завершённую логическую единицу требований, а не случайный кусок текста.

### Этап 1. Парсинг структуры Markdown

Функция `parseDocumentStructure()` сначала проходит по тексту построчно и собирает секции по границам заголовков.

Она дополнительно замечает:

- нумерованные списки;
- маркированные списки;
- строки таблиц;
- код-блоки.

Для каждой секции сохраняется:

- заголовок;
- уровень заголовка;
- путь по заголовкам (`section_path`);
- номер раздела, если он есть (`section_number`);
- диапазон строк в исходном тексте;
- содержимое секции;
- найденные элементы внутри секции.

Это важно, потому что дальше chunk строится уже не из голого текста, а из структурированного блока документа.

### Этап 2. Классификация секции

Дальше функция `classifySection()` определяет тип секции по эвристикам на регулярных выражениях.

То есть система сейчас работает не через ML-классификатор, а через набор правил:

- если текст похож на changelog, статус, метаданные, то это `noise_metadata`;
- если есть признаки API, то это `api_contract`;
- если есть слова про ошибки, то это `error_handling`;
- если есть признаки интерфейса, то это `ui_rule`;
- если есть ограничения и проверки, то это `validation_rule`;
- если секция описывает поведение системы, то это `business_rule`;
- если найдены строки таблицы, то это `table_row`;
- если текст похож на шаги сценария, то это `scenario_step`;
- иначе секция считается `reference_context`.

Важный нюанс: порядок проверок важен. Если секция подходит сразу под несколько типов, она получит тот тип, который проверяется раньше.

### Этап 3. Создание atomic chunk

После классификации из секции создаётся atomic chunk через `createAtomicChunk()`.

В него попадают:

- `id`;
- `doc_id`, `doc_title`;
- `section_path`;
- `section_number`;
- `heading`, `heading_level`;
- `raw_text`, `cleaned_text`;
- `chunk_type`;
- `token_count` как грубая оценка размера;
- `explicit_refs` с явными ссылками вроде:
  - `см. пункт 2.3`;
  - `см. раздел 1.4`;
  - `pageId=12345`;
  - ссылка на другой документ.

То есть chunk хранит не только текст, но и связи с исходной структурой документа.

### Этап 4. Склейка в composite chunk

Не все atomic chunks остаются отдельными. Иногда соседние куски объединяются в один composite chunk.

Это делает `shouldMergeWithPrevious()`.

Склейка происходит по таким правилам:

1. Если предыдущий chunk содержит условную конструкцию, а текущий продолжает её, то они склеиваются.
   Пример: чтобы не разорвать логику вида `если -> то -> иначе`.

2. Если оба куска сами являются частями условной конструкции, они тоже склеиваются.

3. Если это продолжение таблицы требований, куски объединяются.

4. Если типы совпадают и текущий composite ещё не слишком большой, тоже допускается склейка.

Для mergeable типов явно перечислены:

- `business_rule`;
- `ui_rule`;
- `api_contract`;
- `validation_rule`.

И отдельно есть ограничение на размер: если текущий composite уже больше примерно 800 токенов, дальше его не расширяют.

### Что это означает на практике

Здесь граница chunk определяется по смыслу:

- ветка условия не должна быть разрезана пополам;
- таблица требований не должна быть порвана между строками;
- связанные UI-правила или валидации могут храниться вместе;
- служебный шум вообще исключается.

То есть принцип чанкизации такой:

`chunk = не "кусок текста фиксированной длины", а "завершённый логический блок требований"`

## 2. Связи между чанками

Помимо самого текста, система старается сохранить связи между кусками.

### Явные ссылки

Функция `extractExplicitRefs()` извлекает нормативные ссылки из текста:

- ссылки на разделы;
- ссылки на документы;
- `pageId`;
- контекстные ссылки вроде "см. выше".

Эти ссылки сохраняются в `explicit_refs`.

### Дополнительное связывание

В `linkChunks()` есть ещё один механизм:

- строится индекс по заголовкам и requirement id;
- если в тексте одного chunk встречается заголовок другого, между ними создаётся связь через `linked_chunk_ids`.

Это уже не векторный поиск, а явная структурная связанность.

## 3. Как chunk используется в RAG

После чанкизации куски индексируются в PostgreSQL/pgvector.

Это происходит в `server/server.js` и `server/pgvectorStore.mjs`.

При индексации chunk получает:

- `source_type = main` для основного документа;
- `source_type = linked` для связанных страниц;
- embedding;
- metadata;
- explicit refs.

### Поиск работает в три шага

Функция `multiHopStructuredSearch()` делает retrieval так:

1. Сначала ищет primary chunks только в основном документе (`source_type = main`).
2. Потом раскрывает явные ссылки `explicit_refs`.
3. Только если этого мало, добавляет semantic expansion из связанных документов.

Это важная архитектурная идея проекта:

- сначала берём наиболее авторитетные chunks из основного документа;
- потом подтягиваем явно связанные куски;
- и только потом добавляем семантически похожие.

Именно поэтому здесь чанкизация нужна не сама по себе, а как подготовка качественных единиц для retrieval.

## 4. Чанкизация внутри генерации тестовой модели

Отдельно есть ещё одна чанкизация в `server/server.js`, уже после извлечения и построения модели.

Здесь используется функция `splitByStoriesOptimized(modelStructure)`.

Её принцип другой:

- одна `Story` считается одной естественной единицей генерации;
- если в story не больше 5 scenarios, создаётся один chunk режима `FULL`;
- если scenarios больше 5, story режется на батчи по 5 сценариев и chunk получает режим `BATCH`.

Фактически структура тут такая:

- `Feature -> Story -> все Scenarios` для `FULL`;
- `Feature -> Story -> подмножество Scenarios` для `BATCH`.

### Зачем это нужно

Это уже не retrieval-чанки, а генерационные батчи для LLM.

Цель:

- не перегружать модель слишком большой Story;
- сохранить контекст Story;
- уменьшить число дублей;
- дать модели разумный объём задачи за один вызов.

То есть здесь принцип уже такой:

`chunk = удобная порция тестовой модели для одного LLM-вызова`

а не кусок документа для индексации.

## 5. Ещё один важный нюанс

В `server/server.js` есть старые или fallback-механизмы разбиения:

- `semanticChunkByFeatures()`;
- `chunkTextBySize()`.

Но в текущем активном пути генерации модели используется именно `chunkify(reqStringForModel, ...)`, а не простой split по размеру.

Это видно в месте, где формируются `rawChunks`, а затем `reqChunks`.

## 6. Короткий вывод

Если отвечать совсем кратко, принцип чанкизации в проекте такой:

1. Требования режутся по структурным и смысловым границам документа.
2. Куски классифицируются по типу логики: API, UI, validation, business rule и так далее.
3. Логически связанные соседние куски склеиваются, чтобы не разрывать условные ветки и таблицы.
4. Явные ссылки между разделами сохраняются и потом используются в retrieval.
5. После построения тестовой модели она ещё раз режется, но уже по Story и по батчам сценариев для генерации тестов.

Итого:

- для требований chunk означает "смысловой блок документа";
- для генерации тестов chunk означает "батч Story/Scenario для одного вызова LLM".

## 7. Замечание по текущему коду

Есть технический нюанс в логике накопления `previousContext` между чанками модели:

- результаты чанков складываются в `accumulatedModel`;
- затем `extractContext(accumulatedModel)` должен передавать уже построенную структуру в следующий prompt.

Но реализация выглядит не совсем согласованной с тем, что в `accumulatedModel` кладутся массивы по чанкам. Это не меняет сам принцип чанкизации, но может влиять на качество передачи контекста между последовательными chunk-вызовами.
