Реализуй систему обработки требований и генерации тестовой модели как строго последовательный пайплайн, разделяя извлечение контекста и генерацию. Сначала загружай основной документ из Confluence и извлекай все связанные страницы и явные ссылки вида «см. пункт X.Y» или «см. раздел X.Y», потому что в требованиях такие ссылки являются нормативными связями и часто содержат недостающую часть логики сценария. Далее выполняй семантическую чанкизацию не по токенам, а по завершённым единицам требований (действия, правила, API, валидации), чтобы сохранить целостность логики и сделать чанки пригодными для retrieval.

После этого индексируй все чанки в PostgreSQL с pgvector, обязательно сохраняя metadata и явные связи между ними, потому что одной векторной близости недостаточно для восстановления структуры требований и их взаимосвязей. Затем реализуй retrieval в три шага: сначала извлекай primary чанки только из основного документа, затем обязательно разрешай все явные ссылки и подтягивай связанные чанки как обязательный контекст, и только при недостатке информации добавляй ограниченное semantic expansion. Это нужно для того, чтобы минимизировать шум и не заменять структурные связи требований приблизительным семантическим поиском.

На основе собранного контекста строй тестовую модель в виде иерархии Feature → Story → Scenario → Code, используя основной документ как источник истины, а связанные чанки — как уточнение недостающих условий, триггеров и ограничений. Это необходимо, потому что генерация тестов напрямую из текста приводит к потере структуры и неконтролируемым ошибкам, тогда как промежуточная модель обеспечивает трассируемость и воспроизводимость.

Декомпозицию Scenario → Code выполняй через целевой retrieval внутри конкретного сценария, а не через общий семантический поиск по всей базе, чтобы избежать появления нерелевантных проверок. После построения модели генерируй тест-кейсы по слоям (E2E, Integration Frontend, Integration Backend), разделяя их по типам логики, потому что это уменьшает контекст и повышает точность генерации. В конце выполняй нормализацию и валидацию результатов, чтобы привести тест-кейсы к строгому формату и устранить ошибки LLM.

Ключевой принцип системы: сначала восстановить структуру требований через RAG и связи между ними, затем построить формальную тестовую модель, и только после этого генерировать тест-кейсы.
