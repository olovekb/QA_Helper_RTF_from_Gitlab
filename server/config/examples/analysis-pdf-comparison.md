# Анализ качества тест-кейсов из PDF vs текущие примеры

## Ключевые отличия качественных тест-кейсов из PDF

### 1. **ПОДМЕНЫ (MOCKS) В PRECONDITION** ⚠️ КРИТИЧНО ОТСУТСТВУЕТ

**Из PDF:**
```
Precondition:
1. Установить PWA на рабочий стол
2. На устройстве есть защита...
3. Подменить статус-код запроса/rest/personal/bio/devices/bioprint на 2000K
4. Подменить ответ запроса bio/auth на 401 Unauthorized
```

**Текущие примеры:**
- Только описание состояния: "Пользователь авторизован, в ответе метода GET **/rest/...** параметр содержит..."
- НЕТ явных инструкций "Подменить..."

**ЧТО НУЖНО:**
- Добавить в примеры Integration frontend/backend тесты с подменами в precondition
- Обучить агента генерировать подмены для негативных/граничных сценариев
- Формат: "Подменить статус-код запроса **/api/endpoint** на 400" или "Подменить ответ запроса **/api/endpoint** на {error: '...'}"

### 2. **SHARED STEPS** ✅ ЕСТЬ, НО МОЖНО УЛУЧШИТЬ

**Из PDF:**
```
Steps:
1. Shared step [1555]: [M PWA] Авторизация
   1.1. Открыть МП/PWA
   1.2. Пройти онбординг
   1.3. Нажать на кнопку "Войти"
   ...
```

**Текущее состояние:**
- Shared steps поддерживаются в коде
- НО в примерах нет использования shared steps

**ЧТО НУЖНО:**
- Добавить пример E2E теста с shared step в examples
- Показать формат: `{ "sharedStepId": 123 }` в steps

### 3. **ПАРАМЕТРИЗАЦИЯ В STEPS ЧЕРЕЗ СКОБКИ** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Steps:
2. Авторизоваться с помощью (Способ аутентификации)
```

**Текущие примеры:**
- Параметризация только через `{{параметр}}` в expected
- НЕТ параметров прямо в steps

**ЧТО НУЖНО:**
- Добавить пример с параметром в steps: "Ввести {{Код подтверждения}}"
- Обучить агента использовать параметры в steps для вариативности действий

### 4. **DESCRIPTION С ТОЧНЫМИ ССЫЛКАМИ НА ТРЕБОВАНИЯ** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Description:
П. 4.2.1 п.п. 2 -2.2 (2.2.1)
Значение "id" публичного ключа в localStorage очищается...
```

**Текущие примеры:**
- НЕТ поля description
- НЕТ ссылок на конкретные пункты требований

**ЧТО НУЖНО:**
- Добавить поле `description` в примеры (если поддерживается Allure)
- Обучить агента извлекать ссылки на требования из текста и добавлять в description
- Формат: "П. X.Y.Z п.п. A-B (B.1) - описание из требований"

### 5. **ATTACHMENTS (JSON ФАЙЛЫ)** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Attachments:
- client_info.json (application/json)
- alerts (24).json (application/json)
```

**Текущие примеры:**
- НЕТ упоминаний attachments

**ЧТО НУЖНО:**
- Добавить в промпт инструкцию: "Если в требованиях упоминаются JSON ответы API, добавь их как attachments"
- Формат: массив `attachments: [{name: "client_info.json", type: "application/json"}]`

### 6. **ОТДЕЛЬНАЯ СЕКЦИЯ "ПОДМЕНЫ:"** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Подмены:
1. Подменить статус-код второго запроса /pin/auth на 200 OK
2. Подменить статус-код запроса/rest/personal/client_info на 200 OK + тело ответа
```

**Текущие примеры:**
- Подмены только в precondition (если есть)

**ЧТО НУЖНО:**
- Обучить агента выносить подмены в отдельную секцию, если их много (3+)
- Или структурировать precondition с нумерацией для подмен

### 7. **ДЕТАЛЬНЫЕ STEPS С КОНКРЕТНЫМИ ЭЛЕМЕНТАМИ UI** ⚠️ ЧАСТИЧНО

**Из PDF:**
```
Steps:
3. Ввести логин в поле "Введите логин"
4. Нажать на кнопку "Продолжить"
```

**Текущие примеры:**
- Есть детализация, но можно улучшить
- Примеры: "Нажать на кнопку \"Безбумажный офис\"" - хорошо

**ЧТО НУЖНО:**
- Усилить правило: всегда указывать конкретные названия полей/кнопок в кавычках
- Формат: "Ввести {{значение}} в поле \"Название поля\""

### 8. **EXPECTED RESULT С ПРОВЕРКАМИ** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Steps:
3. Проверить очищение значения "id" публичного ключа в localStorage
```

**Текущие примеры:**
- Expected только с реакциями системы
- НЕТ проверок в steps

**ЧТО НУЖНО:**
- Добавить правило: для Integration frontend тестов можно использовать "Проверить..." в steps, если это проверка состояния (localStorage, cookies, DOM)
- Или выносить проверки в expected: "**Проверяется**, что значение 'id' в localStorage очищено"

### 9. **PRECONDITION С НУМЕРАЦИЕЙ** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Precondition:
1. Установить PWA на рабочий стол
2. На устройстве есть защита...
3. Подменить статус-код...
```

**Текущие примеры:**
- Precondition как сплошной текст
- НЕТ структурированной нумерации

**ЧТО НУЖНО:**
- Обучить агента использовать нумерацию в precondition, если пунктов 3+
- Формат: "1. Состояние/действие\n2. Состояние/действие\n3. Подмена..."

### 10. **ISSUES (ССЫЛКИ НА ЗАДАЧИ)** ⚠️ ОТСУТСТВУЕТ

**Из PDF:**
```
Issues:
SBK-15543 SBK-31456
```

**Текущие примеры:**
- НЕТ поля issues

**ЧТО НУЖНО:**
- Если Allure поддерживает issues - добавить в примеры
- Обучить агента извлекать номера задач из требований и добавлять в issues

## ПРИОРИТЕТНЫЕ ИЗМЕНЕНИЯ

### КРИТИЧНО (добавить в примеры и промпты):

1. **Подмены в Precondition** - добавить пример Integration frontend/backend теста с подменами
2. **Shared Steps** - добавить пример E2E теста с shared step
3. **Параметризация в Steps** - добавить пример с параметром в steps: "Ввести {{Код}}"
4. **Description с ссылками** - добавить поле description в примеры (если поддерживается)

### ВАЖНО (улучшить промпты):

5. **Attachments** - добавить правило про JSON attachments
6. **Секция "Подмены:"** - обучить выносить подмены отдельно при большом количестве
7. **Детальные Steps** - усилить правило про конкретные названия элементов UI
8. **Проверки в Steps/Expected** - добавить правило про "Проверить..." для Integration frontend

### ЖЕЛАТЕЛЬНО:

9. **Нумерация в Precondition** - обучить использовать нумерацию при 3+ пунктах
10. **Issues** - добавить поддержку issues (если Allure поддерживает)
