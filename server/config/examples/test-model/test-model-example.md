## Пример тестовой модели — Ингосстрах — МП

### Условные обозначения — кастомные флаги Xmind
- Фронт - узел про UI, клиентскую логику, состояния, обработку ответов и ошибок
- Бэк - узел про сервисы, API, контракты, валидации, работу с БД
- Пользователь - узел про действие пользователя в рамках сценария C1

### Структура модели - как хранится и как синхронизируется с TMS ТестОпс
- Feature - крупный функциональный блок продукта
- Story - сценарный уровень C1 - E2E Tests
- Scenario - интеграционный уровень C2-C3 - Integration Frontend Tests или Integration Backend Tests
- Code - модульный уровень C4 - Unit Tests

## Дерево модели - пример детализации для Feature Платежи

- Платежи - Feature
  - Оплата платежа - Story - C1 - E2E Tests
    - Контекст пользовательского пути - не тест-кейсы, а ориентир процесса
      - Выбрать необходимую категорию
      - Выбрать услугу компании
      - Выбрать компанию
      - Заполнить форму оплаты
      - Перейти на следующий шаг
      - Нажать кнопку подтверждения оплаты
      - Ввести в поиск название необходимой компании
    - Проверки сценарного уровня - C1 - E2E Tests
      - При отправке верифицированного платежа открывается модальное окно OTP
      - При отправке платежа без верификации выполняется переход на успешный экран
      - На успешном экране выполняется вибрация
    - Выбор региона - Scenario - C2-C3 - Integration Frontend Tests
      - Услуги обновляются после получения ответа при смене региона
      - Значения caption и id региона сохраняются и обновляются в LocalStorage
    - Просмотр списка доступных платежей - Scenario - C2-C3 - Integration Frontend Tests
      - Отображается модальное окно Хотите уточнить регион
      - Текст кнопки уточнения региона соответствует макету и требованиям
    - Выбор категории - загрузка и отображение услуг - Scenario - C2-C3 - Integration Frontend Tests
      - Контракт взаимодействия - стартовая строка запроса
        - GET personal/payment_services/search
        - Параметры запроса - group_id, entries, cityId
      - Отображаются группы услуг по массиву groups
      - Отображаются услуги по массиву paymentService
      - Количество отображаемых услуг учитывает параметр entries
      - Отображаются шаблоны из массива templates
      - Отображение иконок использует параметр image
      - Доступны кнопки перехода к QR-коду и реквизитам
    - Отдельные сервисные проверки при необходимости - Scenario - C2-C3 - Integration Backend Tests
      - Если на проекте выделен сервис получения payment_services
        - Контракт ответа для GET personal/payment_services/search соблюдён
        - Валидации параметров group_id и cityId возвращают корректную ошибку
        - Пограничные значения entries обрабатываются стабильно
    - Code - C4 - Unit Tests - по договоренности с разработкой
      - Маппинг ответа payment_services в UI-модель
      - Формирование параметров запроса из выбранных фильтров

## Как это связывается с тест-кейсами в TMS ТестОпс

- Для любого тест-кейса обязателен один Layer
  - E2E Tests - тест-кейсы лежат на уровне Story
  - Integration Frontend Tests и Integration Backend Tests - тест-кейсы лежат на уровне Scenario
- Узел Story или Scenario в модели - это точка покрытия и место хранения тест-кейсов в структуре TMS
- Технические детали в тестовой модели - только стартовая строка запроса и минимум для однозначности
  - без полного curl
  - без заголовков, токенов и тела запроса
  - без перечисления всех вариантов ошибок как текста внутри модели
