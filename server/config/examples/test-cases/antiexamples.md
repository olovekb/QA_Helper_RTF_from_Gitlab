Отглагольное существительное в названии

Название тест-кейса: «Отсутствие уведомления при отключённых пушах»

Неправильный вывод:
{
  "title": "Название начинается с глагола",
  "severity": "error",
  "category": "naming"
}

Почему неправильно: «Отсутствие» — отглагольное существительное, не глагол.
Правило запрещает «Проверить…», «Убедиться…», «Нажать…», и другие глаголы, отвечающие на вопрос «Что сделать?».
Существительные и отглагольные существительные в начале названия допустимы.

---
Требуемый элемент уже есть в тексте

Предусловие содержит:
«Документ {documentId} направлен на согласование сотруднику {employeeId_№2}»

Неправильный вывод:
{
  "title": "Отсутствует описание подготовки документа",
  "recommendation": "Добавьте: 'Документ направлен на согласование сотруднику'",
  "severity": "error",
  "category": "other"
}

Почему неправильно: эта строка уже есть в предусловии.
Перед созданием рекомендации убедись, что элемент отсутствует в тексте.
Если он есть — рекомендацию не создавай.

---
Параметр {{X}} есть в таблице параметров

Параметр может находиться в шаге, ожидаемом результате
или предусловии — правило одно для всех секций.

Пример 1 — параметр в шаге:
Шаг содержит {{Действие}}.
В таблице «### Параметры» есть столбец «Действие» с конкретными значениями.

Пример 2 — параметр в ОР:
ОР содержит {{Ожидаемый результат}}.
В таблице «### Параметры» есть столбец «Ожидаемый результат»
с конкретными значениями для каждой строки.

Неправильный вывод для обоих случаев:
{
  "title": "Непроверяемый ОР / невоспроизводимый шаг",
  "recommendation": "Укажите конкретные значения вместо {{...}}",
  "severity": "error",
  "category": "expected_result"
}

Почему неправильно: {{X}} — ссылка на столбец таблицы параметров.
Если столбец существует и строки содержат конкретные значения —
параметризация валидна, тест воспроизводим.
Проверяй наличие столбца в таблице перед созданием рекомендации.

---
ОР описывает видимое состояние UI без DOM-деталей

ОР содержит: «На кнопке 'Подтвердить' отображается лоадер»

Неправильный вывод:
{
  "title": "ОР недостаточно конкретен",
  "recommendation": "Укажите CSS-селектор или DOM-путь элемента",
  "severity": "warning",
  "category": "expected_result"
}

Почему неправильно: описание видимого состояния элемента — явно допустимо.
Детализация до DOM-уровня, CSS-селекторов и координат не требуется.

---
Значения в моке совпадают с именами полей

В предусловии указан мок, где 'descr': 'descr', 'name': 'name'.

Неправильный вывод:
{
  "title": "Значения в моке — шаблоны без конкретики",
  "recommendation": "Укажите реальные значения вместо 'descr'",
  "severity": "warning",
  "category": "expected_result"
}

Почему неправильно: значения-идентификаторы — допустимая практика тестовых данных.
Совпадение имени поля и значения не делает данные шаблоном.

---
ОР описывает наблюдаемое поведение системы

ОР содержит: «Осуществляется повторный вызов запроса»
или: «Осуществляется переход на страницу X»

Неправильный вывод:
{
  "title": "ОР описывает действие, а не состояние",
  "recommendation": "Укажите конкретный HTTP-метод и URL перехваченного запроса",
  "severity": "error",
  "category": "expected_result"
}

Почему неправильно: наблюдаемое поведение системы — фиксируемый факт,
не субъективная оценка. Требовать технические детали (URL, заголовки)
нужно только если это явная задача теста.

---
Промежуточный ОР отсутствует у шага

В интеграционном тест-кейсе у шага «Нажать кнопку Сохранить»
нет блока «Ожидаемый результат шага».

Неправильный вывод:
{
  "title": "Отсутствует промежуточный ОР шага",
  "recommendation": "Добавьте ожидаемый результат после шага",
  "severity": "warning",
  "category": "expected_result"
}

Почему неправильно: промежуточный ОР после шага — опциональный элемент.
Его отсутствие не является нарушением, если итоговый ОР тест-кейса присутствует.

Моки используются в E2E-тесте

В предусловии E2E-теста указана подмена ответа для запроса.

Неправильный вывод:
{
  "title": "Моки недопустимы в E2E",
  "recommendation": "Уберите подмену запросов — E2E тестирует реальную систему",
  "severity": "error",
  "category": "test_scope"
}

Почему неправильно: использование заглушек и моков для управления
тестовым окружением допустимо на любом слое, включая E2E.

---
Подшаги общего шага приняты за нарушение предусловия

Шаг тест-кейса:
1. Авторизоваться на аккаунте руководителя (общий шаг)
   - Ввести номер телефона
   - Нажать на плашку с ФИО

Неправильный вывод:
{
  "title": "Действия вместо состояния в предусловии",
  "recommendation": "Перенести действия в шаги",
  "severity": "error",
  "category": "steps"
}

Почему неправильно: строки с отступом под «(общий шаг)» — это раскрытие содержимого переиспользуемого шага, не предусловие
и не нарушение атомарности. Анализировать их как самостоятельные шаги не нужно.

Состояние в предусловии принято за пошаговые действия

В предусловии указаны пункты:
1. Создан продукт
2. Создан параметр в модели документа с типом строка
3. Добавлен и опубликован виджет card-account-input в настройках кабинета

Неправильный вывод:
{
  "title": "Действия в предусловии",
  "recommendation": " Предусловие должно описывать состояние системы, а не пошаговые действия. Перенесите шаг «Добавлен на форму контрол card-account-input, привязан параметр модели документа, открыт сайдбар с настройками» в раздел «Шаги»",
  "severity": "error",
  "category": "steps"
}

Почему неправильно: несколько пунктов вида "что сделано?" в предусловии описывают состояние системы, а не шаги.
Такой вариант предусловия не является нарушением
