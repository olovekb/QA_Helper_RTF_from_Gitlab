# Правила статического анализа тест-кейсов

---

## Базовые правила

### Обязательные поля

- **Статус тест-кейса: Review** [ERROR]

  Тест-кейс должен быть в статусе 'Review' для прохождения анализа

- **Заполнен тестовый слой** [ERROR]

  У тест-кейса должен быть указан слой:
  - E2E Tests — для сценарных тестов;
  - Integration frontend Tests;
  - Integration backend Tests.


- **Заполнены приоритет и версия** [ERROR]

  Должны присутствовать значения в полях:
  - Priority — приоритет тест-кейса
  - Version — версия тест-кейса

  Приоритет коррелирует с важностью требования или потенциальной важностью дефекта,
  версия нового тест-кейса соответствует значению поля "Исправлено в версиях" в задаче на написание тестовой документации.


- **Предусловие отражает состояние системы** [WARNING]

  Предварительные условия описывают состояние системы, данных и окружения,
  которое должно быть подготовлено *до начала выполнения тест-кейса*.

  В предусловии допустимы:
  - подготовка тестовых данных (БД, стенд);
  - переход к стартовой точке как состояние ('пользователь авторизован', 'отображается форма платежа');
  - настройка окружения, учетных записей, прав доступа;
  - состояние интеграций/SDK, устройства, предварительное мокирование запросов.


### Теги

- **Наличие тега платформы** [ERROR]

  Тест-кейс должен содержать хотя бы один тег платформы:
  - M — мобильное приложение
  - D — десктоп версия
  - A — адаптивная версия
  - PWA — прогрессивное веб-приложение
  - S — проверки backend


### Правила именования

- **Название начинается не с глагола** [WARNING]

  Название тест-кейса не должно начинаться с глагола (Проверить, Создать, Удалить и т.д.)

- **Название отражает проверку и результат** [WARNING]

  Название тест-кейса описывает проверяемое поведение и синхронизируется с ожидаемым результатом — из названия должно быть понятно, что проверяется и какой итог ожидается.
  Хорошее название:
  - краткое, информативное, сформулировано через существительное или отглагольное существительное ('Отображение ошибки', 'Загрузка справочника');
  - подтверждается ожидаемым результатом

  Примеры хороших названий:
  - "Отображение ошибки при неверном формате email"
  - "Переключение темы оформления"
  - "Валидация поля Email"
  - "Загрузка информации о справочнике"


### Кастомные поля

- **Структура в E2E-Тестах** [ERROR]

  Для E2E тестов обязательны кастомные поля Feature и Story

- **Структура в интеграционных тест-кейсах** [ERROR]

  Для Integration тестов обязательны кастомные поля Feature, Story и Scenario

- **Отсутствие поля Scenario в E2E** [ERROR]

  Для E2E тестов не должно быть кастомного поля Scenario

- **Границы тестовых слоев** [WARNING]

  Тест-кейсы на каждом тестовом слое проверяют контрактные обязательства в рамках своей зоны ответственности:
  - **Integration frontend**-тесты проверяют изолированную логику и взаимодействие ограниченного набора UI-компонентов,
  выполнение бизнес-логики на стороне интерфейса, обработку ошибок и различных входных данных,
  а также контракты взаимодействия с сервисами (вызов запросов с определенными данными, обработка ответов),
  не покрывая полный пользовательский сценарий;
  - **Integration backend**-тесты проверяют работу сервиса или набора сервисов без проверки состояния интерфейса: корректность статусов и тела ответа, обработку ошибок и валидации, бизнес-логикy,
  запись и чтение из базы (если это часть контракта),
  взаимодействие с зависимостями и устойчивость к некорректным/пограничным данным.
  - **E2E-тесты** проверяют сквозной пользовательский сценарий на полностью собранной системе, включая совместную работу фронтенда и бекенда
  и видимый для пользователя результат, без фокуса на внутренней реализации отдельных компонентов или сервисов"


### Ожидаемый результат

- **Заполнен общий ожидаемый результат** [ERROR]

  В тест-кейсе должен быть заполнен общий ожидаемый результат: он отражает итоговое состояние системы после выполнения всех шагов
  и подтверждает достижение цели проверки.


- **Ожидаемый результат не содержит условия** [ERROR]

  Ожидаемый результат должен описывать конкретное и однозначное поведение системы, без условных выражений.
  При необходимости предусмотреть разные сценарии — создаются отдельные тест-кейсы


- **Объективность ожидаемого результата** [WARNING]

  Ожидаемый результат должен быть конкретным и проверяемым,
  без субъективных формулировок ('корректно', 'адекватно', 'удобно', 'эффективно' и т.п.)


- **Проверяемый и конкретный ожидаемый результат** [WARNING]

  Ожидаемый результат должен быть объективным и проверяемым

### Шаги тест-кейса

- **Шаги не содержат условия** [ERROR]

  Описания шагов не должны содержать условную конструкцию 'Если ... то' ('Если отображается модалка, закрыть ее').
  Условия можно вынести в параметры или разделить на разные тест-кейсы


- **Объективность описания шагов** [WARNING]

  Описание шага не должно содержать субъективные слова

- **Шаги с глагола в неопределенной форме** [ERROR]

  Описание шагов должно начинаться с глагола в неопределенной форме (окончания '-ть', '-ться' или '-ти')

- **Отсутствие моков в шагах E2E** [ERROR]

  E2E-тесты не должны содержать шаги с моками

- **Шаги описывают действия** [WARNING]

  Шаг тест-кейса — действие, запускающее проверяемое поведение.
  Каждый шаг начинается с глагола ('Открыть', 'Нажать', 'Ввести'), один шаг описывает одно действие;


- **Проверка API в интеграционных тестах** [WARNING]

  Integration backend/frontend тест-кейсы, проверяющие API, должны содержать HTTP-метод, адрес, необходимые заголовки и тело запроса (если применимо), по возможности — JSON Schema, ссылку на Swagger или другой источник

- **Роли в E2E-тестах** [WARNING]

  E2E-сценарий проверяет один ожидаемый результат для одной роли.
  Действия другой роли необходимо вынести в предусловие, если они подготавливают состояние, или в отдельный тест-кейс
